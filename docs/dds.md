# DDS — модель и правила SCD2 (роль 2)

Код: [sql/dds_load.sql](../sql/dds_load.sql) — DDL и загрузка в одном файле, выполняется
задачей `stg_to_dds` целиком в одной транзакции. Проверки: [scripts/check_dds.py](../scripts/check_dds.py).

## Таблицы

```text
dds.dim_network ─┐                       dds.etl_state      (watermark: last_stg_id)
dds.dim_event_type ┼─< dds.event_versions >── dds.events     dds.load_log       (журнал запусков)
                   │   (SCD2, версии)        (SCD0, ключ)    dds.rejected_observations
```

| Таблица | Зерно | Назначение |
|---|---|---|
| `events` | event_id | Бизнес-ключ USGS, когда и в какой строке STG событие увидели впервые (SCD0) |
| `event_versions` | версия события | Типизированные атрибуты + `valid_from`, `valid_to`, `is_current`, `row_hash` (SCD2) |
| `dim_network`, `dim_event_type` | код | Справочники сетей и типов событий, на них ссылаются внешние ключи |
| `rejected_observations` | stg_id | Наблюдения, не прошедшие проверки, с причиной |
| `etl_state` | процесс | Последний обработанный `stg.earthquake_raw.id` |
| `load_log` | запуск | Сколько строк прочитано, отбраковано, устарело, сколько версий создано/закрыто |

Колонки `event_versions` соответствуют интерфейсу из [contracts.md](contracts.md),
дополнительно: `tsunami_flag boolean` и `alert_level text`.

## Разбор и качество

- Числа из JSON приводятся функцией `dds.json_num`: строка-не-число даёт NULL, а не падение загрузки.
- `type`, `status`, `net` приводятся к нижнему регистру; пустые — `'unknown'`.
- Отбраковываются (в `rejected_observations`): нет времени события; нет координат;
  широта вне [-90, 90] или долгота вне [-180, 180]; магнитуда вне [-3; 10.5];
  глубина вне [-15; 1000] км. NULL магнитуда и глубина допустимы.

## Правила SCD2

1. Обрабатываются строки STG с `id > etl_state.last_stg_id`, порядок — по `id`.
2. `row_hash` = md5 от значимых атрибутов: время, магнитуда и её тип, глубина, координаты,
   place, тип, статус, сеть, tsunami, alert. `loaded_at`, URL и `updated` в хеш не входят,
   поэтому техническое обновление источника новой версии не создаёт.
3. Одно наблюдение на `(event_id, loaded_at)`: берётся строка с наибольшим `source_updated_at`.
4. **Устаревшие данные:** наблюдение пропускается, если его `source_updated_at` меньше,
   чем у текущей версии или у предыдущего наблюдения этого события в той же загрузке.
   Так backfill не откатывает событие назад. **Равное время:** побеждает более позднее наблюдение.
5. Новая версия создаётся, только если хеш отличается от предыдущего принятого состояния.
6. `valid_from` = `loaded_at` (момент, когда наш пайплайн увидел состояние), интервал `[from, to)`.
   Текущая версия: `valid_to IS NULL`, `is_current = true`. `source_updated_at` хранится отдельно.
7. Несколько изменений в одной загрузке дают цепочку версий; последняя — текущая.
8. Версии, отбраковка, журнал и watermark пишутся в одной транзакции. Ошибка откатывает всё,
   повторный запуск ничего не дублирует.

Гарантии на уровне БД: частичный уникальный индекс (одна текущая версия на событие),
`EXCLUDE USING gist` (интервалы версий одного события не пересекаются, нужен `btree_gist`),
`CHECK (is_current = (valid_to IS NULL))`, внешние ключи на `events` и справочники.

## Запросы

```sql
-- Текущее состояние
SELECT * FROM dds.event_versions WHERE is_current;

-- Состояние на момент времени (time travel)
SELECT * FROM dds.event_versions
WHERE '2026-10-27 12:00+00' >= valid_from
  AND '2026-10-27 12:00+00' <  COALESCE(valid_to, 'infinity');

-- История одного события
SELECT valid_from, valid_to, magnitude, review_status
FROM dds.event_versions WHERE event_id = 'us7000abcd' ORDER BY valid_from;

-- Последние запуски
SELECT * FROM dds.load_log ORDER BY load_id DESC LIMIT 10;
```

## Проверки

`python scripts/check_dds.py --local` (или внутри Airflow, см. README) создаёт
временную БД, кладёт контролируемые наблюдения в STG и проверяет: новое событие;
неизменившийся повтор; изменение магнитуды и статуса; два изменения в одной загрузке;
позднюю устаревшую запись из backfill; равное время обновления; отбраковку;
одну текущую версию и смыкание интервалов; time travel; откат при ошибке; повторный запуск.

## Что получает роль 3

Витрины читают `dds.event_versions` (и при необходимости справочники). Счётчики событий
и карта — только по `is_current` и `event_type = 'earthquake'`, иначе SCD2 завысит числа.
Историю уточнений даёт сравнение первой (минимальный `valid_from`) и текущей версии события.
Названия колонок совпадают с интерфейсом в [contracts.md](contracts.md), плюс `tsunami_flag`
и `alert_level`.
